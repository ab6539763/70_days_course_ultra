## 一、公司与产品背景

### 1.1 公司信息

- **公司全称**:蓬远科技(北京)有限公司
- **品牌名**:蓬远智能
- **成立时间**:故事开始前3年(即陈铭入职时,公司已运营3年)
- **公司定位**:一家专注于"企业级大模型应用落地"的AI应用公司,不做基础大模型预训练,专注于把通用大模型(接入 OpenAI、DeepSeek、通义千问等API,以及后期私有化部署开源模型)转化为可以在制造、金融、零售等行业客户内部真正跑起来的应用系统。
- **办公地点**:北京市海淀区中关村某科技园区,3层小楼的整个二层,工位约60个。
- **公司规模**:故事开始时全公司约45人,技术团队(含产品、测试、运维)约22人。
- **业务模式**:面向企业客户做"AI应用中台+行业定制化交付"的乙方模式,既卖平台使用权(SaaS/私有化部署),也接项目制定制开发。
- **核心产品代号**:**苍穹**(英文/工程代号 `cangqiong`,内部仓库名 `cangqiong-platform`)
- **产品全称**:苍穹企业级智能体中台(Cangqiong Enterprise Agent Platform)
- **产品愿景**(挂在工位墙上的海报语):"让每一家企业,都拥有自己的AI大脑。"

- **第一阶段(Day1-14)**:公司内训期,陈铭还没有直接写苍穹的代码,但所有内训小项目都是"未来会长成苍穹一部分"的雏形练习(通讯录管理系统 → 未来的用户/会话管理;命令行AI助手 → 未来的对话引擎)。
- **第二阶段(Day15-24)**:苍穹项目正式立项,陈铭加入"对话引擎小组",产出**苍穹 0.1 版**——一个网页版对话产品(对话引擎层 + 基础API + 极简前端)。
- **第三阶段(Day25-38)**:苍穹升级到**0.5 版**,补上 RAG检索引擎层,交付第一个正式客户项目——**海纳制造集团企业知识库问答系统**。
- **第四阶段(Day39-50)**:苍穹升级到**0.8 版**,补上 Agent编排层,交付第二个客户级项目——**多Agent智能办公助手**(先内部试用,再向客户祺瑞集团交付试点)。
- **第五阶段(Day51-57)**:苍穹升级到**0.9 版**,补上模型接入层的私有化能力(微调+本地部署),交付第三个客户项目——**御风金融本地化合规问答模型**。
- **第六阶段(Day58-70)**:苍穹1.0正式版全量整合,交付旗舰级客户项目——**寰宇集团全域智能体平台**,随后是产品发布、复盘与陈铭的转正/晋升。

## 三、技术栈与工程规范(全程严格保持一致)

### 3.1 技术栈清单

- **语言**:Python 3.11(课程内文字统一写"Python 3.10+",实际生产环境锁定3.11.6)
- **包管理**:前期用 `venv` + `pip` + `requirements.txt`;Day10提及 `conda` 作为备选;不引入 poetry/uv,保持零基础学员友好度。
- **大模型API**:优先使用 **DeepSeek**(`deepseek-chat` / `deepseek-reasoner`)和**通义千问**(`qwen-plus` / `qwen-max`,通过阿里云DashScope兼容OpenAI接口调用)作为主力低成本模型;示例代码中会展示"OpenAI SDK 通用调用方式"(因为DeepSeek、Qwen等都提供OpenAI兼容接口),偶尔对比GPT-4o、Claude作为"如果预算充足"的选项。
- **Web框架**:FastAPI + Uvicorn
- **数据校验**:Pydantic v2
- **数据库**:SQLite(开发期)→ PostgreSQL(Day56生产部署起);ORM统一用 SQLAlchemy 2.0
- **向量数据库**:Chroma(默认,轻量、易于教学)→ Day29对比 Milvus / FAISS / Pinecone 优劣,苍穹平台生产环境最终选型为 **Milvus**(为后续企业级多租户、大规模数据做准备),但教学示例仍以 Chroma 为主,Milvus 在项目集成日出现。
- **LLM应用框架**:LangChain(`langchain` + `langchain-core` + `langchain-community` + `langchain-openai`)、LangGraph、LlamaIndex(仅Day35对比使用)。
- **Embedding模型**:教学阶段使用 `BAAI/bge-large-zh-v1.5`(中文效果好、可本地部署)以及 DashScope/OpenAI 提供的 `text-embedding-v3` 作为对比。
- **Rerank模型**:`BAAI/bge-reranker-large`。
- **微调框架**:LLaMA-Factory,微调基座模型选定为 **Qwen2.5-7B-Instruct**。
- **推理部署**:Ollama(本地/开发)、vLLM(生产/高并发)。
- **容器化**:Docker + Docker Compose;生产环境Day56起部署到云服务器(阿里云ECS,示例IP统一使用文档保留地址风格,如 `10.0.x.x` 内网 / `x.x.x.x` 占位公网,不使用真实IP)。
- **前端**:HTML5 + CSS3 + 原生JavaScript(`fetch`、`EventSource`处理SSE),不引入React/Vue等重框架,贴合零基础学员的"够用就好"原则,但工程规范(模块划分、注释、错误处理)按照企业级标准要求。
- **版本控制**:Git + 公司自建GitLab(对内称"蓬远GitLab"),分支规范:`main`(生产)/ `develop`(集成)/ `feature/xxx`(功能分支)/ `hotfix/xxx`。
- **项目管理**:公司使用飞书项目(类似Jira),任务编号格式 `CQ-<三位数字>`(CQ = CangQiong),例如 `CQ-101`。
- **代码规范**:遵循PEP8;函数/类必须有中文docstring;关键业务逻辑必须有行内中文注释解释"为什么这么做"而不仅是"这行代码做了什么"。

## 四、每日课件统一写作规范(格式模板,所有天必须遵循)

每篇课件是一个独立的 Markdown 文件,建议顺序包含以下模块(可根据当天内容灵活调整比例,但模块不能缺):

1. **标题与元信息**:第X天 / 星期几(以陈铭入职当天为第1天、周一起算,连续70天不跳过周末——公司培训期强度较高,不安排完整双休,但会在文中体现"周末强度略降、有半天休整"这种真实感,不要显得不合理)、对应Sprint、对应飞书任务号。
2. **【旁白】**:至少一处以旁白/画外音形式给出上下文解读(可以是"编者按"式的口吻,解读这一天在全局中的位置、意义,埋下悬念或点出与前后天的关联),不少于300字。
3. **晨会纪要 / 今日目标**:模拟真实晨会场景(站会),包含昨天进展、今天目标、风险点。
4. **需求文档(PRD)**(当天如涉及新功能/新项目):背景、用户故事、功能列表(表格)、非功能需求、验收标准。若当天是纯技术自学日,可以是"技术调研需求"或"内部工具需求"形式代替。
5. **架构设计图**:用 Mermaid 绘制(`graph` / `flowchart` / `sequenceDiagram` / `classDiagram` 等适用图形),并配文字解读。
6. **流程图**:用 Mermaid `flowchart` 绘制当天核心技术流程(算法流程、数据流、请求生命周期等)。
7. **示意图**:用 Mermaid 或结构化 ASCII 图辅助讲解抽象概念(如注意力机制类比图、token化示意、向量空间示意等)。
8. **课堂笔记(正文主体,占比最大)**:分"上午"、"下午"、"晚自习"三段,严格对应课程原始大纲的教学内容,展开讲解,包含大量具体例子、常见报错与排查、与前后知识点的呼应。
9. **代码实战**:多个完整代码文件,每个文件都有详尽中文注释,禁止"...省略..."字样,代码必须是完整可读的实现(允许在极长的重复性样板代码处做合理精简,但核心逻辑不能省略)。
10. **今日复盘**:陈铭的反思、与老王/林悦等人的对话片段、遇到的坑。
11. **课后作业**:不少于5道题,覆盖概念题、代码题、思考题,难度递进。
12. **作业参考答案**:逐题给出详细解答(代码题给出完整代码与解析)。
13. **明日预告**:呼应下一天内容,制造连续感。

**字数要求**:每篇课件正文(不含代码)不少于30000字;代码与文档合计构成完整的一天课件。**语言要求**:全部使用简体中文,行文要像真实培训机构讲师和资深工程师共同打磨出来的教材,避免"作为一个AI"、"我将为您"等痕迹,避免每天用完全相同的句式开头。

## 六、写作红线(务必遵守)

1. 不出现"作为AI/作为语言模型/我是一个AI助手"等自指表述。
2. 不出现日期具体到"20XX年X月X日"这种可能暴露AI生成套话的写法,统一用"入职第X天"、"周X"、"Sprint X 第X天"这种相对时间表达,若确需公历日期,可用不指名具体年份的"7月的第二周"等模糊化表达,或直接跳过日期只标"Day N"。
3. 每天课件必须能与前一天结尾、后一天开头对上,不能有情节断裂。
4. 所有客户名、人物名、产品名严格按本文档,不得随意更改或新造(除非该文档明确留出"可自行补充"的空间,如某天需要一个新的小配角)。
5. 代码要保持技术上大体正确、可运行或接近可运行(允许合理简化以适应教学,但不能出现明显反常识的错误代码而不加说明)。
6. 每天结尾的"作业参考答案"必须真正给出答案与解析,不能只写"请参考课堂内容"。
